# Central authority, offline resilience and selective peer assistance

Proposed v0.3 architecture refinement; no new runtime capability or approval implied. Retain a single logical authoritative PostgreSQL database behind Hive.Server on the existing LAN Linux Docker stack. Initially one PostgreSQL primary and one API instance are sufficient as a deployment baseline, not a measured capacity or availability guarantee. SQLite remains endpoint-local. Do not replicate authoritative state to peers, elect workstation leaders or introduce multi-master conflict resolution. Optional server redundancy and peer-assisted distribution are separately gated, not prerequisites of P7 or P8.

## Ownership and failure semantics

| Data | Authority / storage | Disconnected behaviour |
|---|---|---|
| Users, roles, credential escrow, approvals, policy, asset allocations, tickets, maps, validation and audit | PostgreSQL via API only | No new authoritative mutation; no vault checkout or secret cache |
| Telemetry, inventory, health and operation observations | Device originates; PostgreSQL stores accepted history | Continue bounded local observation and queue; mark central state stale |
| Workload protection, deployment execution journal | Local guard is enforcement authority; central policy/lease authorises start | Protection continues; no new privileged execution without fresh lease; reconcile uncertain running installs, never kill or blindly retry |
| Notifications | PostgreSQL recipient state; per-user DPAPI cache | Display last known pending actions; queue acknowledgement intent; do not claim central completion |
| Support | PostgreSQL ticket/assignment; per-user protected draft | Draft only, explicit pending state; submit after reauthentication and current permission check |
| Packages | Central immutable content store, approved signed manifest and digest | Retain eligible cached bytes; cache presence never authorises install |
| Floor plans and quality records | Central approved revisions | No offline privileged edits; any separately approved read cache is scoped, time-limited and clearly stale |

Device certificate and user authentication remain separate. No workstation has database credentials or direct access to another workstation's SQLite, user cache, audit records or credential store. Do not silently convert outages to peer trust. Use existing mTLS HTTPS, LocalJwt, SignalR hints and durable reconciliation.

## Offline queue and recovery

Extend current SQLite machine queue and per-user protected cache, not a second master. Persist typed observations before acknowledging local collection; unique event ID plus enrolled device/boot/sequence, occurred/received UTC, schema and source. Server commits accepted events and dedupe keys transactionally before acknowledging; retries safe, reject revoked identities and invalid payloads. At-least-once transport with idempotent effects, not exactly-once delivery. User intents carry original user subject, idempotency key and resource revision; reauthenticate and re-evaluate permissions, applicability and version at submission; conflicting changes require explicit user review, never last-writer-wins. Separate durable critical transitions from coalescible telemetry. Configurable byte/age quotas, reserve critical journal capacity, aggregate/drop oldest routine samples only with explicit gap counters; if critical persistence fails, flag degraded state and refuse new privileged work. Never queue passwords, raw logs or case data.

On reconnect: authenticate and negotiate capability, reconcile policy/leases/revocations, send bounded critical batches then routine observations, fetch authoritative delta or snapshot reset, re-evaluate pending intents and resume eligible downloads. Apply jitter/exponential backoff, per-device quotas and fleet recovery throttles. Queue acknowledgements only after durable server commit; tolerate restart and duplicate delivery. Stale protection or missing server authority blocks installation, assisted RDP, new wake permits, policy changes and allocations. Local monitoring, existing protection and safe local diagnostics continue. Show last successful sync, backlog, drops and local vs central timestamps. A DB or API outage must not mark offline devices powered off, healthy or compliant.

## Selective peer assistance

Wake relay (E3) already follows this model: server issues short-lived target-specific permit to an approved online agent via outbound sync; relay emits bounded magic packet only on configured local interface/subnet. No generic commands, inbound management listener, public broadcasts or autonomous peer control. Require fresh target heartbeat to confirm wake; separate RDP authorisation. See [Fleet intelligence](../03_Implementation/FLEET_INTELLIGENCE.md).

Peer-assisted package delivery (optional E12, after E7 and E2) is a transport optimisation only. Central API remains source of entitlement, approved version, manifest, lease and immutable digest. Start with normal central HTTPS, measure bottlenecks, consider a dedicated site cache before endpoint peers. If justified, pilot LAN-only, same approved security zone, explicit IT/vendor redistribution licence approval and opt-in nominated cache hosts; default disabled. No automatic LAN discovery, DHT, torrents, Internet tracker, broadcast discovery or tailnet/isolated network bridging. Server tracks authorised cache advertisements and issues short-lived receiver/source/package-digest-bound transfer grants. Dedicated restricted cache process/listener only after firewall and threat review; existing agent retains no inbound management listener. Mutual TLS validates both enrolled identities and server-signed grant, audience, expiry, nonce, current entitlement/revocation (online check or fail closed), interface and byte limits. No bearer token in URL/logs. Peers serve only complete verified immutable bytes from protected approved cache by digest, never arbitrary paths/files. No credentials, policy, telemetry, notifications or evidence shared. Receiver verifies complete SHA256 and approved manifest/signature/publisher independently before staging; cache supplier is never trusted for approval. Optional chunk integrity requires signed chunk metadata; final whole-file verification always mandatory. Range/ETag bound to digest, temporary file/quota, atomic promotion, corrupted peer quarantine, central fallback, bounded retries and audit source/receiver/digest/outcome. Withdrawal/revocation/kill switch stops new grants and transfers; expire/recheck grants, purge according to policy. Broker still requires fresh central install lease and local protection. No peer-only installation during outage.

Throttle per source/receiver/site, avoid metered links, enforce disk/network/CPU budget and defer serving under active/unknown protected workload; no evidence scratch. Measure central egress, LAN traffic, completion time and forensic throughput. Illustrative 10 GB x 50 = 500 GB central egress without caching; ideal one seed = 10 GB central egress, not total network traffic or promised saving. Failure to improve measured performance is a reason not to deploy.

Distributed forensic compute is a future separate feasibility project, not part of E1–E12: Hive may coordinate authorised Cordon workers later, with evidence-access/chain-of-custody design, isolation, validated deterministic outputs, job provenance, resource consent and quality/security approval. No evidence transfer or remote job execution authorised by this specification.

## Capacity and availability

Use existing PostgreSQL/Npgsql with pooled bounded connections, batched inserts, time-indexed queries, retention/aggregation and backpressure. At 100 devices/10 seconds, 10 logical samples/s or 864,000/day; at 500 devices/10 seconds, 50/s or 4,320,000/day. Actual rows/transactions/storage vary by collectors, batch size, schema, WAL/index overhead and payload. Benchmark concurrent dashboard, inventory, health, audit and reconnect bursts against real PostgreSQL before sizing. Consider native time partitioning only with measured need, test pruning and migrations; use existing proposed retention (7d raw, 30d minute, 180d hourly, separately approved audit retention). No Redis, RabbitMQ, distributed SQL or new database engine by default.

Initial recovery: existing single primary/API plus independent encrypted tested backups and monitored WAL archiving/PITR if configured; agree RPO/RTO (current proposed 24h/4h, not guarantees), backup artifact generations, config, audit and protected escrow/JWT/TLS keys as appropriate; signing keys separately secured. Recovery is not high availability. Optional E13 after P7 and demonstrated operational need: PostgreSQL physical streaming standby on independent host/failure domain; async by default candidate with explicitly accepted loss window, sync only if durability target justifies latency/write availability tradeoff. Replication slots/WAL retention bounded and monitored, lag, health and backup age alerts. Replication is not backup and propagates deletion/corruption. Use stable private DB endpoint, fenced single writable primary, documented manual failover initially, no auto promotion without tested quorum/fencing and split-brain prevention. Do not use standby for authorisation or other stale-sensitive reads. Test planned switchover, crash, partition, stale primary fencing, standby lag, failback/rejoin and PITR separately. Never accept conflicting writable primaries; choose unavailable over inconsistent privileged decisions.

Full HA also needs redundant API instances, authenticated TLS/mTLS ingress compatible with existing certificate boundary, shared protected secrets and consistent immutable artifact storage, DB-coordinated worker leases/outbox and cross-instance SignalR strategy (or durable polling fallback). Current in-process assumptions must be reviewed and tested; no new backplane automatically selected. After failover invalidate uncertain leases, recheck emergency stop/revocations, reconcile agent journals and ensure no duplicate privileged execution. Measure actual RPO/RTO across DB/API/artifacts/keys; restore escrow only with matching independently protected key versions. PostgreSQL stays LAN-private even in P8. Do not make HA or peer transport a blocker for LAN release.
