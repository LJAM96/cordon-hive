# Signed Hive lifecycle, software centre and quality assurance (FR19, FR24–FR25)

## Agent and component lifecycle

Extend existing ReleaseManifestCrypto, package store, deployment lease, protection guard, broker, downloader and emergency stop; do not repurpose arbitrary installer execution. Separate Hive component release type, independent release signing key and approved publisher trust. Manifest binds component, version, architecture, OS/API/IPC compatibility range, package hash/size, signer, install profile, dependencies, monotonic release sequence, expiry/revocation and recovery reference. Verify detached manifest and SHA-256 plus Authenticode publisher chain via Windows trust API; define offline trust bundle, revocation freshness and key rotation; fail closed when trust unknown. Never disable verification for offline operation. Publisher cannot approve own release. Signed installer/bootstrap updater runs outside target process; narrowly scoped service identity, ACL-protected staging, fresh lease, maintenance mutex and recheck. Stop/restart only Hive components with explicit consent and no loss of workload protection; broker refuses if local safety state cannot survive restart. No automatic OS reboot. Agent heartbeat/version plus service health and protocol negotiation after install; bounded timeout, journal and recovery if power loss or API outage. Recover known-good independently signed version only by explicit approved rollback permit (anti-downgrade by default), preserve device identity/SQLite/locks, fail closed if unsafe. Widget/app updates per session without focus theft; broker changes require separate privileged validation. Rings: lab pilot → limited → broader; pause on failures, emergency stop invalidates pending leases, never blindly kill running installer. Offline import via approved transfer, signed package and trust chain; no external mandatory service. Evaluate existing eligible app packaging/Velopack vs MSI separately; no new dependency assumed.

## Software Centre

User-facing catalogue extends P3/P5 and existing SoftwarePage/UpdatesPage, not new package pipeline. Product cards include vendor, category, description, approved release notes, applicability, available/installed version(s), size, dependencies, release status, validation summary, approval scope and install/request/upgrade/defer status. Historical releases only installable while explicitly approved and compatible; withdrawn/prohibited remain visible as history, not eligible. User initiation creates server-validated request with device binding, role, applicability, current policy, licence entitlement where recorded, dependency plan and idempotency; server creates existing typed deployment target or approval request. No local admin/password requirement or arbitrary args. Software requests route through service desk. Select approved maintenance window UTC/display local, reconfirm eligibility and protected state at execution. Cache content-addressed immutable packages on managed scratch, ACLs, quotas/LRU excluding active or pinned artifacts, Range/ETag resume, verify on each install; never peer-share without separate approval. Release notes plain safe text; no external fetch by agent. Use existing deployment states and history, signed release manifests, independent approval and ring concurrency/bandwidth caps. Rollback is an independently validated package with documented compatibility and data migration limitations, not generic uninstall. Never perform unattended unvalidated EXE/MSIX/portable install; P5 MSI baseline first. Dependency DAG must be approved and acyclic; each prerequisite independently validated; failure halts dependent work. Notifications complete only on observed verified state.

## Validation register

Quality record immutable revision: product/release, module/plugin versions, intended use and validation scope, tested OS/build and configuration, report reference/hash, method limitations, approving identity, effective date, review due, status and supersedes. Separate vendor release from lab approval; draft → under review → approved/rejected → superseded/withdrawn/expired-review (policy defines consequence). Prohibited version overrides ordinary eligibility; scoped exceptions require independent approver, reason, effective bounds and audit, never override integrity failure or workload protection. Review reminders do not silently approve newer release. Approved configuration profile contains allowlisted keys/values and deterministic canonical digest, never secrets or case locations. Inventory adapter reads only approved settings/binaries with file-size/I/O budget and no evidence drive scan; SHA256 controlled executable/module digest with signer, source and last observed time, mismatch/unknown explicitly reported. Missing module or incompatible OS/configuration not compliant. No automatic repair or overwrite. Report links are internal allowlisted references with access checks; immutable report attachments subject to service desk upload policy. Separate approval from uploader, record revocations and policy changes. Report as-of date uses effective-dated approvals, exemptions, observations and recorded-at timestamps; show last known observed state with gaps/coverage, not claim continuous proof. Export CSV/JSONL or reviewed report with scope, query, UTC, policy revision, provenance and caveats; protect formula injection and restrict download, audit export. Supports quality workflows; does not confer ISO/IEC 17025 or FSR compliance.

## Optional package transport optimisation
Central HTTPS is baseline. E12 may pilot site caching or centrally authorised peer-assisted immutable package delivery only after E2/E7 and a demonstrated bottleneck. See [Resilience and peer assistance](../02_Architecture/RESILIENCE_AND_PEER_ASSIST.md); no peer sharing by default, no relaxation of signatures, independent approval, fresh installation lease or local workload guard.
